# Deep copy drafting for several users: K8V4_DEEP_ALL on GDN RecoverSSM (2026-11-19)

Branch `b70/deep-all` = `b70/spec-034` rebased onto `b70/vllm-034`, plus `b70/gdn-recoverssm` (RecoverSSM for the GDN
layers, `K8V4_GDN_RECOVERSSM`, unchanged), plus two commits that let more than one request draft deep. Ported from the
B70 stack this work is measured against (-24 `B70_DEEP_ALL`, -25/-26 RecoverSSM). Off unless set; with every knob unset
`launch.sh` prints the same command as before (`test_launch_profiles`). Lossless: the target verifies every drafted
token; copy and edit outputs below are identical to the non-deep run.

| knob (default off) | what | where |
|---|---|---|
| `K8V4_DEEP_ALL=1` | with `K8V4_DEEP_DRAFT`: two or more requests draft the deep depth (15) while ALL of them are copying | `k8v4_v030/deep_draft.py`, `launch.sh` |
| `K8V4_DEEP_ALL=any` | the deep depth while ANY request copies; the others verify their MTP drafts plus rejectable filler in the same uniform step | `k8v4_v030/deep_draft.py`, `ngram_lookup.py` |
| `K8V4_GDN_RECOVERSSM=1` (b70/gdn-recoverssm) | one GDN state block per request at any draft depth; needed for long contexts | `k8v4_v030/gdn_recoverssm.py` and friends |

Measured config: `K8V4_DEEP_DRAFT=12,16 K8V4_DEEP_ALL=1 K8V4_GDN_RECOVERSSM=1 K8V4_MAMBA_SSM_DTYPE=float16` on
`b70/all-034` config A (`K8V4_MAX_SEQS=4`, prefix caching, util 0.96, `XE2_KV_S1_SPLITS=32`, embed host, draft
skip-shared, GDN heads, W4A8 all/onednn, draft last row) + `K8V4_DRAFT_VOCAB` (64K) + `K8V4_ONEDNN_DETERMINISTIC=1`.

## Why deep drafting stopped at one request

`K8V4_DEEP_DRAFT` drafts 15 copied tokens for a lone copying request; with two or more requests everything fell back to
MTP depth 3. vLLM 0.34 reserves one GDN state block per draft position for every running request
(`MambaSpec.num_speculative_blocks` = `num_speculative_tokens`), and on this stack a hybrid page is a 1-2K-token KV page
in each of three GDN cache groups: a request at depth 15 holds 48 pages, about 100K tokens of KV, so four 63K requests
drafting deep do not fit. RecoverSSM keeps one state slot per request at any depth: KV at depth 15 with four sequences
is 508,655 tokens (config A + draft vocab without RecoverSSM: 384,176 at depth 6; config B, deep drafting for one
request without RecoverSSM: 290,741).

## Which RecoverSSM: `K8V4_GDN_RECOVERSSM` (b70/gdn-recoverssm), not this branch's first port

Two ports of our -25/-26 RecoverSSM were written independently on 2026-11-19: `K8V4_GDN_RECOVERSSM`
(b70/gdn-recoverssm e0bcdf3 / 7d6bc97, decode-push agent) and `K8V4_RECOVERSSM` (this branch's first version,
3de5af7, kept as branch `b70/deep-all-ownrssm`). Both carry the same code from our 0.34 port, so the designs agree
point for point:

| | K8V4_GDN_RECOVERSSM (kept) | K8V4_RECOVERSSM (dropped) |
|---|---|---|
| verify kernel | vllm-xpu-kernels 0.1.17 SYCL RecoverSSM as `_k8v4_rssm.verify`, record-row patch, `compile_rssm.sh` (compile image) | same kernel, same patch, built from a Dockerfile |
| conv stage / mixed steps | `_xpu_C.causal_conv1d_spec` on the checkpoint column; prefill rows through the stock op on compacted rows | identical |
| commit | vLLM Triton commit + plan + conv compaction (`rssm_gdn.py`, `rssm_kernels.py`) | identical kernels |
| record-row staging | fresh pinned buffer per step (`async_tensor_h2d`, our -26 fix) | identical |
| splices | 8: arch list, `supports_replayssm` on both models and the MTP draft, the `models/qwen3_5` package comment that moves vLLM's model-info cache key, layer install, XPU dispatch, profiling-step reset | 6: same minus the cache-key line (a stale model-info cache could report `supports_replayssm` False) |
| depth | nothing depth-specific: replay buffer and commit window are `num_speculative_tokens + 1` | same |
| measured | depth 3/6, lossless up to rounding, GDN 6.3 -> 3.5 ms per 4-user step, KV 384K -> 509K with `K8V4_MAMBA_SSM_DTYPE=float16` | not run |

`K8V4_GDN_RECOVERSSM` is the one already measured and it also moves the model-info cache key, so this branch now
sits on it unchanged (the RecoverSSM files on `b70/deep-all` are byte-identical to `b70/gdn-recoverssm`), and only
the deep drafting commits are new. Depth 15 needs nothing extra from it; the measurements below run it at depth 15.
The measured config adds `K8V4_MAMBA_SSM_DTYPE=float16` (b70/gdn-state-dtype), as the decode-push measurement did.

## Deep drafting for several requests (`K8V4_DEEP_ALL`)

- `1` (our -24 `B70_DEEP_ALL`): the scheduler runs copy detection (the last 12 tokens occur earlier in the request,
  held for two steps) for every scheduled request each step; when all of them are copying the step drafts 15. The
  speculator runs the GPU n-gram lookup for every request: matched requests take their copied tokens (one-hot draft
  logits), the others keep MTP drafts in the same step; the MTP decode steps are skipped only when every request
  matched. Otherwise the batch keeps its schedule depth (3; a lone request keeps the existing one-request logic).
- `any`: the deep depth while at least one request copies. The MTP decode then runs only the batch's MTP depth (from
  `num_speculative_tokens_per_batch_size`, 3); a request without a full-length copy verifies its 3 MTP drafts plus 12
  rejectable filler tokens (its last MTP draft repeated, one-hot draft logits). The step keeps one uniform query width
  and replays the 4 x 16 decode graph instead of a ragged step (their `FULL_DECODE_ONLY` graphs need a uniform width,
  ragged steps run eager; our stack's ragged per-request-depth prototype lost ~22 ms per step to raggedness).
- Verify of 16 rows on the K8/V4 decode kernel: `K8V4_VERIFY_CHUNK` (8, set by `launch.sh` with deep drafting).
- Graph capture: `launch.sh` adds `n x 16` for n = 2..MAX_SEQS (32, 48, 64 at four sequences); the
  `get_decode_cudagraph_query_lens` hook gives the deep width every batch size.
- `B70_SPEC_BASE` (our per-request state-block trimming) is not ported: RecoverSSM makes it unnecessary (our -25 runs it
  at 0).

## Measurements

One B70, Swift 1.5, the local test harness end to end over HTTP, image `k8v4-up:rssm-v2` with source
`b70/test-deep-all` (= `b70/test-rssm` + the two deep-all commits). Windows: `dpBase` = the measured config without deep
drafting (`K8V4_MTP_SHARED_DEPTH=3`, RecoverSSM + float16 state on), `dpAll` = the deep-all config, `dpsmoke` = the same
deep-all config one window earlier. Copy workloads: `copyprobe.py` (one request at a time, greedy, 1,200 tokens) and
`copy4.py` (concurrent requests behind their own filler context, greedy, 1,200 tokens, aggregate while all decode).
Our stack: prod -24 / -25 on its own model (gates g24 / g25, `copyprobe-prod24/25`), same scripts.

  184.8 and the RecoverSSM base 183.7: unchanged. Deep drafting adds nothing to ordinary steps (same width, same graph).
- Copy and edit texts: identical to `dpBase` in all 18 copy/edit outputs (copyprobe 4, c8 4, m8 2, c63 4, m63 2, c2x63
  2), and the two deep-all windows (`dpsmoke`, `dpAll`) are identical in all 8 copyprobe outputs (ordinary ones too)
  with `K8V4_ONEDNN_DETERMINISTIC=1`. Ordinary texts differ between base and deep-all: the two configs have different
  page sizes (`num_speculative_tokens` 6 vs 15 widens the conv window, attention block 1,152 vs 1,280 tokens), so

(770 vs 840 at 8K, 426 vs 456-464 at 63K, 350 vs 384 at 2 x 63K) and above -24 everywhere; the gap is the general
decode-step gap of their stack (ordinary four users 184 vs 206). Mixed 2 + 2 at 8K is level with -25 (315 vs 319):
neither `K8V4_DEEP_ALL=1` nor our stack draft deep unless every request copies.

## Mixed copy/write: `K8V4_DEEP_ALL=any` (window `dpAny`, same config with `K8V4_DEEP_ALL=any`)

| workload | base | `=1` | **`=any`** | our -25 |
|---|---:|---:|---:|---:|
| 2 copying + 2 writing, 8K, aggregate | 321.1 | 314.7 | **449.3** (+40%) | 319 |
| copy-code / edit-rename (copying users) | 98.3 / 98.9 | 98.4 / 97.8 | **217.5 / 143.8** | |
| essay / story (writing users) | 69.6 / 62.5 | 67.8 / 62.4 | 61.1 / 58.7 (-12% / -6%) | |
| 2 copying + 2 writing, 63K, aggregate | 213.0 | 214.9 | **248.8** (+17%) | |
| copy-code / edit-rename | 66.6 / 66.4 | 66.6 / 66.2 | 122.0 / 82.5 | |
| essay / story | 46.9 / 45.3 | 47.8 / 45.1 | 41.3 / 39.5 (-12% / -13%) | |
| 4 users all copying, 8K | 399.0 | 770.0 | 749.4 | 840 |

`any` turns a mixed group from "nobody drafts deep" into "the copying users draft deep": +40% aggregate at 8K, +17% at
63K, copying users 1.2-2.2x, copy texts identical to the base. The writing users pay for the 16-row verify (their 3
MTP drafts are followed by 12 filler rows, two KV reads per full-attention layer instead of one): -6..-13%. That is the
same fairness trade-off our stack measured for its ragged per-request-depth prototype (mix4 8K 324 -> 441, ordinary
users -12..-15%), which our prod did not adopt; here it comes without a ragged eager step. With all requests copying
`any` behaves like `=1` (749 vs 770, single runs). Writing users' texts differ from `=1` (their verify is 16 rows wide,
so the target's logits are computed in a different batch shape; greedy ties), the copy texts do not.

Recommendation: `K8V4_DEEP_ALL=1` as the default-safe choice (never slows a writing user); `any` where aggregate
throughput of mixed agent traffic matters more than the writing users' speed.
