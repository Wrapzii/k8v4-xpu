# MLP W4A8 wiring fix — October 2, 2026

The vLLM 0.30 deployment requested `K8V4_PREFILL_GEMM=w4a8`, but its backend never invoked the installer. Saved model graphs contained W4A16 GEMMs and no W4A8 calls. Enabling the actual MLP path reduced fresh 128K first-token latency from **110.81 to 102.15 seconds**, or **1,157 to 1,255 prompt tokens/s**. This is an observed 8.5% throughput improvement, not the requested 2,000 tokens/s.

## Implementation

`backend.py` now invokes `install_if_requested()` before model compilation. The hook wraps vLLM's `XPUwNa16LinearKernel` only for MLP projections. Checkpoint weights stay GPTQ INT4; this change quantizes MLP activations per token to INT8 for large batches. Attention and GDN projections retain their original W4A16 kernels. Vision, MTP count, and the native K8/V4 decode library are unchanged.

The compiled model calls an opaque `k8v4_prefill::mlp_gemm` operation. It chooses precision using the **actual runtime row count**, preventing a symbolic branch from choosing one precision for the entire compiled range:

- At most 128 rows: native W4A16.
- More than 128 rows: compiled per-token quantization followed by native W4A8.
- W4A8 disabled: W4A16, including calls through a previously cached opaque graph.

Pure decode batches stay below the threshold. A mixed prefill/decode batch above 128 total rows uses W4A8 for all its MLP rows; this is a batch gate, not a per-request gate.

The launcher mounts the current Python package and sets a separate `VLLM_CACHE_ROOT` namespace (`w4a8-wired-v1` by default). This prevents old AOT graphs from silently bypassing the newly installed hook. Changing source may require a fresh compilation on restart. Set `K8V4_PREFILL_GEMM=w4a16` before starting a new container to opt out.

## Measurements

Same Swift baked checkpoint, two B60s, TP2, MTP6, thinking disabled, concurrency one, 4,224 scheduled tokens, fused GPU KV gather, and synchronous oneDNN prefill. GPU clock ceilings and power settings were unchanged. Fresh requests used different front nonces and reported **zero cached prompt tokens**. Effective throughput is prompt tokens divided by time to first token, including serving overhead.

| fresh prompt tokens | configuration | first token | effective prefill | decode |
| ---: | --- | ---: | ---: | ---: |
| 128,197 | Before: W4A16 despite requested W4A8 | 110.810 s | 1,156.9 tok/s | 81.70 tok/s |
| 128,197 | Wired MLP W4A8, first request | 103.518 s | 1,238.4 tok/s | 77.65 tok/s |
| 128,197 | Wired MLP W4A8, fresh confirmation | 102.153 s | 1,254.9 tok/s | 78.02 tok/s |

The confirmation saves 8.66 seconds (7.8% lower latency). These are individual observations, not a statistical sweep. Generated answers and speculative acceptance differ, so the decode differences do not isolate GEMM performance.

The cached 128K request measured 4.398 seconds to first token and 81.45 tok/s decode; 124,608 prompt tokens were cached. A warmed 8K request measured 2.079 seconds and 139.53 tok/s. The prior warmed 8K samples measured 2.334–2.468 seconds and 133.33–134.73 tok/s. Cached throughput must not be described as cold GPU prefill throughput.

Reported shared KV capacity decreased from **869,121 to 860,324 tokens**, about **1.01%**. The batch cap remains 4,224. Four active sequences are allowed; four fully occupied 262,144-token windows do not fit. No full overlapping agent workload was rerun for this fix, so these results do not establish unchanged concurrency latency.

All five generated coding answers passed syntax and embedded behavior checks and stopped naturally. Twenty-seven relevant CPU tests passed, including alternating runtime sizes through a compiled graph and disabling W4A8 after graph compilation. This is targeted validation, not a general quality-equivalence evaluation.

## Other candidates checked

The available paged FlashAttention kernel was **slower** than oneDNN for 4,224 query tokens against 128,000 KV tokens: 78.713 versus 72.404 ms median. Both passed three sampled FP32 oracle checks. The [probe script](../bench/prefill_flash_paged.py) reproduces this shape inside the serving image with the model stopped; it blocks the quadratic fallback. These isolated attention timings exclude KV gathering and the rest of the model. The unpaged causal head-dimension-256 specialization was unavailable in the installed kernel package; its fallback attempted quadratic attention and exhausted GPU memory in the isolated probe. The deployment retains oneDNN.

An earlier attempt to extend W4A8 to output projections was also affected by the missing installer. Its timings cannot establish whether that policy helps. This release enables only the original MLP policy.

The previous asynchronous SDPA experiment showed no full-model improvement and remains disabled. The fused gather remains enabled for its lower temporary GPU memory use; its earlier full-model timing difference was small and provisional.
