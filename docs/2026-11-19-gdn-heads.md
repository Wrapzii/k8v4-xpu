# Head-parallel GDN prefill kernels (K8V4_GDN_HEADS)

Off by default. `K8V4_GDN_HEADS=1` makes `launch.sh` mount a rebuilt
`libgdn_attn_kernels_xe_2.so` over the image's vllm-xpu-kernels copy. The
default command line is unchanged (asserted in `test_launch_profiles`).

## Why

Two GDN prefill kernels in vllm-xpu-kernels, `chunk_compute_A_kernel` and
`chunk_compute_wu_kernel`, give each work-group one 64-token chunk and loop
over all 48 value heads inside it. A short prompt has few chunks (200 tokens =
4), so 4 work-groups run 48 serial head iterations each while the rest of the
GPU idles. That is about 20-30 ms per request across the 48 GDN layers at any
prompt length below ~2K tokens: most of the fixed cost of an agent turn's
prefill.

`native/gdn_heads_patch.py` spreads flattened (chunk, v_head) units over the
same persistent work-groups. Each unit runs exactly the per-(chunk, head) code
it ran before, on the same data, so the outputs are **bit-identical**; only the
work-group to unit assignment changes. Upstream main still has the serial loop
(an open upstream PR makes the same split plus a re-tiling that is not
bit-identical).

## Build and use

```
K8V4_COMPILE_IMAGE=k8v4-compile-2026 k8v4_v030/compile_gdn.sh   # -> build/libgdn_attn_kernels_xe_2.so
K8V4_TP=1 K8V4_GDN_HEADS=1 MODEL_DIR=... k8v4_v030/launch.sh
```

- The script clones vllm-xpu-kernels at the commit pinned for the release the
  compile image ships (0.1.14.1 for vLLM 0.30, v0.1.17 for vLLM 0.34), applies
  the splice and builds the GDN target only (CPU, network, 2-3 min at one job,
  one icpx job peaks near 18 GB). Build against the same vLLM image you serve.
- `K8V4_GDN_PATCH=0` builds the unpatched control library
  (`build/libgdn_attn_kernels_xe_2.stock-rebuild.so`).
- `K8V4_GDN_HEADS_LIB` points launch.sh at another library path.
- `tools/gdn_exact_v030.py run OUT.pt` / `cmp A.pt B.pt` checks bit identity
  (run once with the image's library, once with the rebuilt one mounted).

## Measured (one B70, Swift 1.5 Qwen3.8-27B)

Measured 2026-11-19 on vLLM 0.34 (b70/test-v034 = their stack moved to 0.34,
image k8v4-up:v034-1508198, xk 0.1.17), TP1, `K8V4_MAX_SEQS=4
K8V4_PREFIX_CACHING=1 K8V4_MAX_MODEL_LEN=131072 K8V4_GPU_MEMORY_UTILIZATION=0.96`,
same image and cache for both runs; only `K8V4_GDN_HEADS` differs. The card's
own power limit (no xpu-smi step).

**Bit identity** (`tools/gdn_exact_v030.py`, fused `gdn_attention` op, 8 cases:
65 / 200 / 508 / 2,047 / 8,192 tokens, 3 and 8 sequences, with initial state):
stock image library vs patched rebuild: out, conv state and ssm state
**bitwise equal in all 24 tensors**. The unpatched rebuild is also bitwise equal
to the stock library (so the compiler, oneAPI 2026.0, changes nothing either).

GDN op time per prefill, x48 layers (same test):

| tokens | stock | heads |
|---|---|---|
| 65 | 28.6 ms | 8.9 ms |
| 200 | 31.1 ms | 9.7 ms |
| 508 | 36.6 ms | 13.1 ms |
| 2,047 | 64.0 ms | 49.2 ms |
| 8,192 | 191.4 ms | 193.6 ms |
| 8 seqs, 1,251 | 59.8 ms | 40.2 ms |

**End to end over HTTP**, cold (nonce at the start of the prompt), one request
at a time, median of 5, streamed time to first token (`ttft_probe.py`):

| prompt tokens | stock | K8V4_GDN_HEADS=1 | change |
|---|---|---|---|
| 93 | 142.8 ms | 107.0 ms | -25% |
| 192 | 171.4 ms | 122.2 ms | -29% |
| 388 | 245.1 ms | 211.3 ms | -14% |
| 774 | 432.9 ms | 407.9 ms | -6% |
| 1,495 | 767.5 ms | 754.8 ms | -2% |
| 5,828 | 2,983.9 ms | 2,982.6 ms | 0 |
| 8,189 cold (prefill_curve, 2 reps) | 4.27 s (1,911 tok/s) | 4.26 s (1,919 tok/s) | 0 |
| 65,531 cold | 43.86 s (1,493 tok/s) | 43.86 s (1,494 tok/s) | 0 |

Their coding client (`bench/serve_coding.py`, 2K and 8K, repeats hit the prefix
cache): a warm agent turn that computes only the 74-token suffix of a cached
2,186-token prompt takes 0.148-0.155 s of prefill on stock and 0.115-0.119 s
with the patch (-22%); the 1,856-token suffix of the 8K prompt 1.014 -> 1.000 s.
EXACT battery 8/9 in both runs (same as the 0.34 baseline). Decode is not
touched (the patched kernels run only in chunked prefill).

So: a fixed ~20-35 ms per short prefill goes away, which is a quarter of a
short turn's time to first token; nothing changes at 6K tokens and above.
