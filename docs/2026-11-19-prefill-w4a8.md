# W4A8 prefill on all GPTQ linears, s4 library path, fused quantizers — November 19, 2026

One Arc Pro B70, Swift 1.5 (Qwen3.8-27B GPTQ int4 g128, bf16), TP1, vLLM 0.34 base (`b70/vllm-034`),
`K8V4_MAX_SEQS=4 K8V4_PREFIX_CACHING=1 K8V4_MAX_MODEL_LEN=131072 K8V4_GPU_MEMORY_UTILIZATION=0.96
XE2_KV_S1_SPLITS=32 K8V4_UPLOAD_SLICE_MB=128`, stock power limit (no xpu-smi step).
Every knob below is off by default; with none set the launch command and the math are unchanged.

## Knobs

| knob | default | what it does |
|---|---|---|
| `K8V4_W4A8_LAYERS` | `mlp` | which GPTQ projection families take the int8 prefill GEMM above 128 rows: comma list of `mlp`, `attn` (`self_attn`, the MTP draft's included), `gdn` (`linear_attn`), `other` (e.g. `mtp.fc`), or `all` |
| `K8V4_W4A8_KERNEL` | `xpu` | `onednn`: the selected layers' nibbles are flipped once at load to s4 without a zero point (u4 with zero point 8 is s4 of the same nibbles XOR 0x8) and both their prefill (int8) and decode (bf16) GEMMs run `libk8v4_w4a8.so` (`K8V4_W4A8_LIB`, mounted by `launch.sh`; build recipe `k8v4_v030/native/w4a8/`) |
| `K8V4_W4A8_AGROUP` | `0` | with `onednn`: one activation scale per token **and** per 32/64/128 input channels instead of one per token |
| `K8V4_W4A8_FUSED` | unset | with `onednn` + `AGROUP`: `silu` computes SiLU(gate)·up inside the down projection's quantizer; `gnorm` computes the GDN gated RMSNorm inside out_proj's quantizer (needs `gdn` in `LAYERS`) |
| `K8V4_NCONTIG_RE` | unset | regex: dense linears whose prefix matches keep a [K, N]-contiguous weight (bitwise-reproducible oneDNN matmul; `in_proj_ba`) — separate branch |

Each set value is passed through by `launch.sh` and gets its own compile-cache namespace.

## Why: where the prefill GEMM time goes (GEMM microbenchmark, M = 4,224 rows, one forward pass)

Sum over the model's 64 MLP, 48 GDN and 16 attention layers (`bench/w4a8bench.py`-style, random weights with
the real shapes, median of 15, bf16 activations):

| configuration | GEMM + quantizer time per 4,224-token chunk | GEMM-only tok/s |
|---|---:|---:|
| main today: MLP w4a8 (stock op), attention + GDN w4a16 | ~1,444 ms | ~2,925 |
| all layers, stock `int4_gemm_w4a8` | 1,295 ms | 3,262 |
| all layers, s4 library, per-token scales (Triton quantizer) | 948 ms | 4,457 |
| all layers, s4 library, 64-channel scales (Triton quantizer) | 1,116 ms | 3,785 |

- The stock w4a8 op hands oneDNN a weight zero point and a source zero point; without them the same GEMM is
  24-31% faster on every shape (e.g. `mlp.gate_up` 8.86 -> 6.16 ms, `attn.qkv` 3.91 -> 2.85 ms).
- Writing bf16 directly from the GEMM beats fp16 output + cast (6.16 vs 8.20 ms on `mlp.gate_up`).
- The compiled-torch per-token quantizer took 0.33-0.84 ms per layer and the grouped one 0.89-3.2 ms; the
  one-pass Triton kernels take 0.17-0.54 ms.
- Decode (7 and 28 rows) through the library's bf16 x s4 GEMM is **bit-identical** to the stock
  `int4_gemm_w4a16` on all seven shapes and 4-20% faster per call.
- The int8 activation error vs the w4a16 GEMM (max abs / max): per token 0.9-1.2e-2, 64-channel groups 0.7-0.85e-2.

## End to end (cold 63K prompt over HTTP, `conc64.py` user 0)

the local test harness window, one cold nonce'd 63,000-token chat prompt, `max_tokens` 1, time to first token;
image `k8v4-up:v034-1508198` (0.34 base) with the package mounted from `b70/test-w4a8-034`.
EXACT is the harness's 9-question exact-answer battery (thinking off).

| label | knobs (on top of the base config) | cold 63K prefill | EXACT | 1-user decode |

| w34base | none (this branch, knobs unset) | 44.0 s, **1,431 tok/s** | - | 55.3 tok/s |

decode GEMMs of the s4 layers are bit-identical to stock (microbenchmark above).

## Profile: where a cold 63K prefill spends its time

Torch profiler over the whole prefill (`--profiler-config.profiler=torch`, `record_shapes`), device time:

| bucket | base (MLP-only stock w4a8) | `LAYERS=all` stock op (w34all) | `LAYERS=all KERNEL=onednn` (w34odpt) |
|---|---:|---:|---:|
| wall time under the profiler | 41.8 s | 37.5 s | 31.3 s |
| int4 GEMM kernels (all linears, incl. MTP draft) | 20.8 s (MLP w4a8 ~10.5, attention + GDN w4a16 10.3) | 15.1 s | 13.9 s |
| fp16 -> bf16 cast of the stock w4a8 output | 2.3 s | 3.4 s | 0 (bf16 written by the GEMM) |
| activation quantizers | 1.2 s (compiled torch) | 1.8 s (compiled torch) | 0.9 s (Triton) |
| oneDNN SDPA (`micro_sdpa`, full-attention layers) | 11.3 s | 11.0 s | 10.5 s |
| GDN chunk kernels | ~2.7 s | ~2.6 s | ~2.6 s |

With the stock `int4_gemm_w4a8`, a third of what W4A8 saves on the GEMM itself goes back to the fp16 output cast
and the compiled-torch quantizer; the library path removes the cast and the Triton quantizer halves the rest.

The SDPA is ~84 TFLOPS on a 6,400 x 57,024 x 6-head call (2.2 TFLOP in 26.5 ms), i.e. close to the card's
power-capped bf16 rate; it did not get faster with 8,192-token chunks (10.5 s at both sizes) and 8,192 tokens cost
~26K tokens of KV (335,966 vs ~362K). The GEMMs are the remaining prefill lever in this scope.

## Numerics

- Defaults: unchanged (byte-identical command, same ops).
- `LAYERS` beyond `mlp`: the KV cache and the GDN state now come from int8-activation GEMMs (numerics change).
- `KERNEL=onednn`: prefill numerics change (no zero points, different oneDNN build); decode GEMMs are bit-identical
  to stock.
- `AGROUP`: closer to the w4a16 GEMM than per-token scales, slower.

## Not ported

- Our fused post-attention add+RMSNorm producer (`B70_W4A8_ADDNORM`): it needs the decoder layer forward
  rewritten; left out.
- Our 9-16-row decode catalog edit (`mk_dec16.py`) is in the library build but only covers fp16 x int4; this
  stack decodes in bf16, so it does not apply.
- `AGROUP=64` with `FUSED=silu,gnorm` measured 1,883 tok/s vs 1,980 for per-token scales: the grouped GEMM is
  ~15% slower and the fusions did not win that back. The window that isolates the fusions (`AGROUP=64` without
  `FUSED`) was not run, so their own gain is not measured.

## Summary

Cold 63K prefill, same image and config: 1,431-1,511 tok/s with the knobs unset, **1,980 tok/s** with
`K8V4_W4A8_LAYERS=all K8V4_W4A8_KERNEL=onednn` (+31-38%). EXACT stayed 8/9 in every window (the base also
scores 8/9). This is single runs, not a sweep. QualityBench was not run (speed first, per the plan).
