Branch `b70/vllm-034` (from main d804707). Test branch `b70/test-v034` = this branch plus the

The SYCL runtime in the 0.34 image is 2026.1.2; Intel publishes no `2026.1.2` devel image, so the compile image
uses `intel/oneapi:2026.1.0-devel-ubuntu24.04` (same 2026.1 line, same libsycl.so.9 ABI). The compile scripts
look for `compiler/2026.1` first and still fall back to `2026.0` and `latest`. `K8V4_COMPILE_IMAGE` (default
`k8v4-compile-2026`, unchanged) lets a host keep a 0.30 and a 0.34 compile image side by side.

## Package name

The package stays `k8v4_v030`. Renaming it touches every import, the backend path that the platform splice
returns, `launch.sh`'s bind mount, the Dockerfiles and all tests, and it would make every open branch on top of
main conflict. The name is now a historical label; the README says which vLLM it targets.

## Attention-backend API, 0.30 -> 0.34

- `AttentionMetadataBuilder.set_kernel_block_size` is **gone** in 0.34. The runner now picks the kernel block per
  KV-cache group (`prepare_kernel_block_sizes` / `AttentionGroup.create_metadata_builders`) and constructs the
  builder with a spec whose `block_size` already is the kernel block. With `MultipleOf(64)` the manager block is
  accepted, so 0.34 never splits a K8/V4 block. The builder now binds the kernel block in `__init__` when the base
  class has no `set_kernel_block_size`, and keeps the old override for 0.30 (both call `_bind_kernel_block`).
- `get_supported_kernel_block_sizes` takes an optional `kv_cache_spec` in 0.34; the backend's zero-arg static
  method now takes it as an optional argument (a zero-argument static method raised TypeError on 0.34).
- Unchanged: `AttentionCGSupport.UNIFORM_BATCH`, `MultipleOf`, `customize_spec` / `state_content_bytes`,
  `CommonAttentionMetadata.block_table_tensor` / `seq_lens_cpu_upper_bound`, `_init_reorder_batch_threshold(...,
  supports_spec_as_decode=True)`, `AttentionImpl.forward(..., output_scale, output_block_scale)`,
  `do_kv_cache_update(layer, key, value, kv_cache, slot_mapping)`, `register_backend(AttentionBackendEnum.CUSTOM)`.
- The 0.34 KV-cache allocator builds per-layer `[B, H, N, C]` views from `state_content_bytes`, which is the
  K8/V4 `[block, head, token, 396]` layout the backend already asserts.

## Benchmarks

One B70 (the card, stock 230 W PL2, no xpu-smi power step), Swift 1.5 GPTQ int4 bake, their TP1 launch.sh argv
(upverbatim.py) + `K8V4_MAX_SEQS=4 K8V4_PREFIX_CACHING=1 K8V4_MAX_MODEL_LEN=131072 K8V4_GPU_MEMORY_UTILIZATION=0.96`
+ `-e K8V4_UPLOAD_SLICE_MB=128`. our local test harness, 63,000-token prompts, 512 output tokens, thinking off.

| run | image | KV tokens (blocks) | 63K cold prefill | 1-user decode | 4-user agg (per-user) | warm TTFT 1 / 4 users | exact | needle |
|---|---|---|---|---|---|---|---|---|
| 0.30 main+sliced, util 0.92 (upsim, reference only) | k8v4-up:sliced-f236b7f | 322,406 (214) | 1,432 | 47.0 | 23.1 (6.1, pathological) | 3.64 / 11.60 s | 8/9 | 6/6 |
| **0.34 main+sliced** (v034base) | k8v4-up:v034-1508198 | 349,525 (232) | **1,511** | 50.7 | 87.7 (21.9) | **1.67 / 5.98 s** | 8/9 | 6/6 |
| 0.30 e2e (sliced + PR3 kernels + multi-page S1, SPLITS=32), e2eu96 | k8v4-up:e2e-749618a | 357,058 (237) | 1,425 | 63.3 | 127.4 (28.6) | 3.74 / 11.57 s | 8/9 | 6/6 |
| **0.34 e2e** (same commits cherry-picked, SPLITS=32), e2e034 | k8v4-up:e2e034-3431825 | 349,525 (232) | **1,514** | **73.4** | **131.1 (32.6)** | **1.67 / 5.88 s** | 8/9 | 6/6 |

There is no 0.30 main+sliced run at util 0.96; the like-for-like 0.30 comparison is the e2e row (the coordinator's
reference, e2eu96). The base row shows the port by itself loads and serves; decode differences there are mostly the
S1 kernel work, which only the e2e rows carry.

0.34 vs 0.30, like for like (e2e rows): KV -2.1% (232 vs 237 blocks of 2112 tokens: 0.34 reports 14.76 GiB for the
model and 12.32 GiB for KV), cold 63K prefill +6.2%, one-user decode +16%, 4-user aggregate +2.9%, warm TTFT
-55% at 1 user and -49% at 4 users. Stall test (a new user's 63K cold prefill while one decodes): 44.9 s vs 47.9 s.

Their coding client (`bench/serve_coding.py`, lengths 2K/8K/32K/127.7K, 448 tokens, 3 repeats after a cold
warmup; medians of the 3 repeats, which hit the prefix cache):

| length | 0.30 e2eu96 TTFT / decode | 0.34 e2e034 TTFT / decode |
|---|---|---|
| 2K | 1.17 s / 119.5 tok/s | 0.19 s / 128.1 tok/s |
| 8K | 2.18 s / 115.8 | 1.04 s / 123.9 |
| 32K | 2.02 s / 107.9 | 0.47 s / 118.0 |
| 127.7K | 4.61 s / 84.7 | 1.79 s / 86.7 |

The warm-TTFT gain is vLLM 0.34's own prefix-cache path for the hybrid model (same K8/V4 backend code); decode
gains come with the 0.34 runner / torch 2.15 (identical kernels and sources on both sides). EXACT and NEEDLE are
unchanged (8/9 and 6/6 on both; the harness prints only the total, so whether the miss is the same prompt is not recorded).

### 0.34-native feature: draft depth by batch size

0.34's MRV2 autoregressive speculator honours `num_speculative_tokens_per_batch_size` (on 0.30 the field was
accepted but the V2 runner never applied it). With the opt-in `K8V4_MTP_SHARED_DEPTH=3` from
b70/mtp-shared-depth (`[[1,1,6],[2,4,3]]`, capture sizes `[7,8,12,14,16,21,28]`) on the 0.34 integration image:

| | e2e034 (depth 6 always) | e2e034d3 (6 alone / 3 shared) |
|---|---|---|
| KV tokens | 349,525 | 351,031 |
| 63K cold prefill | 1,514 | 1,486 |
| 1-user decode | 73.4 | 69.0 |
| 4-user aggregate (per user) | 131.1 (32.6) | **158.3 (38.7), +21%** |
| warm TTFT 1 / 4 users | 1.67 / 5.88 s | 1.66 / 5.89 s |

Verified through vLLM's `/metrics` counters (`spec_decode_num_draft_tokens_total / spec_decode_num_drafts_total`,
`v034-depthcheck.py`): 1 request 6.00 draft tokens per draft, 4 concurrent requests 3.00, back to 6.00 at 1. The
one-user row drafts 6 in both columns; its 73.4 -> 69.0 (-6%) is one sample each, so it is either run-to-run
spread or a small cost of the dynamic-depth path (e.g. the extra capture sizes); not settled. Lossless (target verifies every draft).
