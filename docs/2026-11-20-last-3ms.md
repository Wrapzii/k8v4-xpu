# The last 3 ms: their 4-user 63K decode step against ours (2026-11-20)

Goal (user): their stack's 4 x 63K decode step from 58 ms (`s1vFB`) to under our stack's ~55 ms.

Result: **54.1 ms against our 54.1 ms**, measured in the same hour with the same client: a tie at four users.
At one user theirs is 6% faster (40.2 vs 42.8 ms). A clear four-user win is not reachable with knobs. Both stacks
keep the GPU 99.7-99.8% busy, so what is left is kernel time (attention S1, RecoverSSM verify, GEMMs).

## How step time was measured

- `bench/decode_step_timer.py` (new) keeps N users on warm 63K prefixes (the `conc64.py` prompts, greedy,
  `ignore_eos`) and runs 3 rounds of 512 tokens. In the window where all N decode, the gap between SSE chunks is one
  engine step: MTP streams a step's accepted tokens together. It reports p50 / mean / p10 / p90 at 0.1 ms. Rounds
  agree within 0.1 ms, and p10-p90 spans 0.7 ms. The harness `gap p50` rounds to whole ms (54 / 55 / 58 hide
  0.5 ms either way).
- `bench/gpu_busy_fdinfo.py` (new) reads GPU busy share without a profiler. It uses the xe driver's per-client
  counters in `/proc/<pid>/fdinfo` (`drm-cycles-ccs` / `drm-total-cycles-ccs`), over the same windows, as
  a local analysis script does for prod.
- Every candidate run: config A + draft vocab + `K8V4_ONEDNN_DETERMINISTIC=1` + `XE2_KV_S1_FAST=1` +
  `XE2_KV_BATCH_REQS=1`, image `k8v4-up:rssm-v2`, test tree `b70/test-last3ms`. End-to-end windows:
  the local test harness (= the local test harness + step timer; `TESTS="exact users custom mt"`, `USERS="1 4"`,
  `MT_LEVELS="1 4"`, `CONV_PER_CLIENT=1`, `SEED_BASE=20261118`, plus the coding client), the local test harness (ours
  then theirs, step + busy), the local test harness (torch profile, graphs on).

## Best combined config

Config A (`K8V4_MAX_SEQS=4 K8V4_PREFIX_CACHING=1 K8V4_MAX_MODEL_LEN=131072 K8V4_GPU_MEMORY_UTILIZATION=0.96
XE2_KV_S1_SPLITS=32 K8V4_EMBED_HOST=1 K8V4_DRAFT_SKIP_SHARED=1 K8V4_GDN_HEADS=1 K8V4_W4A8_LAYERS=all
K8V4_W4A8_KERNEL=onednn K8V4_DRAFT_LASTROW=1 K8V4_MTP_SHARED_DEPTH=3`) +
`K8V4_DRAFT_VOCAB=<64K ids> K8V4_ONEDNN_DETERMINISTIC=1 XE2_KV_S1_FAST=1 XE2_KV_BATCH_REQS=1
K8V4_MAMBA_SSM_DTYPE=float16 K8V4_GDN_RECOVERSSM=1 K8V4_DRAFT_FUSED_DECODE=1 K8V4_DTYPE=float16` (= `l3h`): 4 users
54.7 ms, 1 user 41.2 ms. For the lowest four-user step, use the 32K vocabulary (`l3best`, 54.1 / 40.2 ms), at
some cost in acceptance. Image: `k8v4-up:rssm-v2` with `build/` from `b70/test-last3ms` (`libxe2_kv.so` of
s1-rows, `libk8v4_rssm.so`). Numerics: fp16 GDN state and fp16 activations differ from their bf16 / fp32-state
default, as our prod does. Everything else is lossless or bit-identical. QualityBench not run (user: speed first).

## What would still beat ours at four users

All of it is kernel work, in order of size: the verify S1 at 70% of its read floor (about 4.6 ms; the kernel
agent's s1-rows notes list what has been tried), the RecoverSSM verify at about 3x its read floor (about 1.1 ms; it
needs a different loop structure, not launch geometry), and the decode GEMMs at 83-90% of floor (about 2 ms in
total; no oneDNN catalog row found better).
