# K8/V4 KV-cache drift: noise floor, controlled A/B, K-vs-V attribution (2026-11-20)

Question: how much do next-token distributions move because the KV cache is stored as int8 K + int4 V
("K8V4"), separately from W4A8 activations and run-to-run noise? Which half causes it, and can an opt-in
change fix it?

**Verdict:** the K8V4 format has a real quality cost, and **all of it comes from the int4 V**. The int8 K
is at the noise floor.
- Offline, on real Swift 1.5 activations with no server noise: storing V as int4 moves the attention output
  by **6.8-7.2 %** (relative L2, last 128 rows, rms over the 16 full-attention layers). The int8 K moves it by
  **0.5 %**, and fp8 K/V by **2.7 %**. So K8V4 is **2.5-2.7x fp8**.
- End to end, with the noise removed (determinism on, copied compile cache; same-config restarts give KL 0):
  - K8V4 against a bf16 cache: median next-token KL **0.006-0.008**. fp8 gets **0.0016-0.0018**, about
    **4x less**.
  - K8V4 also brings rare large flips. One of the 40 cuts goes from `'\n\n'` 0.52 to `' delta'` 0.999
    (8.2 nats). That cut is the earlier "10-nat code cut".
  - The same drift appears when K/V are only *rounded* through K8V4 on the stock bf16 attention kernel, so it is
    the storage format, not their kernels.
- **Fix (opt-in, built and measured on their backend):** `K8V4_KV_ROTATE=v` stores V in a Hadamard basis.
  It needs no kernel change, no layout change and no capacity change.
  - Median KL 0.0067 to 0.0046, mean 0.27 to 0.026, the 8-nat flip gone, top-1 36/40 to 39/40.
  - Cost: +0.6 % (4 users) and +1.1 % (1 user) decode step.
  - `kv` gets the median to 0.0032 at +1.1 % / +1.8 %.
  - Neither reaches fp8's median, because int4 V has a floor.
- A V-only change gets closer to bf16 at a capacity cost: int4 V with 64-wide groups and fp16 scales (-2 % KV
  tokens), or int8 V (-24 % KV tokens). Both were measured as exact format simulations, not built as kernels.

## Setup

- Hardware and model: one B70 (the card), Swift 1.5 (Qwen3.8-27B GPTQ int4, 16 full-attention layers, 4 KV heads
  of 256), image `k8v4-up:all034-575ee85`. The mounted tree is `b70/test-kv-drift`: `b70/all-034` plus a
  test-only capture hook and `K8V4_KV_ROTATE`.
- Launch: their TP1 launch with `K8V4_MAX_SEQS=4 K8V4_PREFIX_CACHING=1 K8V4_MAX_MODEL_LEN=131072
  K8V4_GPU_MEMORY_UTILIZATION=0.96`, MTP depth 6, prefix caching on. **Every arm sets
  `K8V4_ONEDNN_DETERMINISTIC=1`.** W4A8 is fixed per comparison: `off` (`K8V4_PREFILL_GEMM=w4a16`), `g64` (all
  layers, oneDNN s4, `K8V4_W4A8_AGROUP=64`) or `pt` (their default per-token MLP).
- Metric: a local analysis script, the QualityBench agent's tool, unchanged.
  - It reads the next-token top-20 logprobs at the same 40 cuts: 20 prose cuts from 1.5K to 43K tokens and
    20 code cuts from 2.2K to 35K.
  - KL is taken over the union of the two top-20 lists. Tables give median / mean / max KL and top-1 agreement
    out of 40.
  - The mean is dominated by one or two knife-edge cuts, so read the median and the per-cut table together.
- **The bf16 and fp8 arms run vLLM's stock XPU FlashAttention backend** (`--kv-cache-dtype auto|fp8`).
  - With those dtypes, their backend module is never imported. That module is what installs W4A8 and the
    determinism flag.
  - So these arms load a test-only `sitecustomize.py` (`K8V4_FORCE_INSTALL=1`) that runs the same installers.
    The serve logs confirm `k8v4_w4a8: installer active ...` and `mkldnn.deterministic = True` in every arm.
  - The same file can wrap `FlashAttentionImpl.do_kv_cache_update` (`K8V4_FAKEQ=<k>,<v>`). Each cache write then
    goes through a candidate format: quantize, then dequantize, using exactly the K8V4 store arithmetic. This
    isolates the storage format from the K8V4 kernels (int8 Q in decode, fp16 oneDNN prefill).

## What the earlier arms measured

These points explain why the QualityBench numbers did not add up:
- **`d1` (bf16 KV) never ran W4A8.** With `--kv-cache-dtype=auto` the K8V4 backend module is not imported, and
  W4A8 is installed from that module. `d1`'s serve log has no `k8v4_w4a8: ... installer active` line, while
  `a1`'s does.
  - So `a1` vs `d1` = K8V4 **plus** per-token W4A8 **plus** the missing determinism flag.
  - The same applies to any other `--kv-cache-dtype auto/fp8` run of their stack.
- **`e1` ("W4A8 off") still ran W4A8.** Removing the `K8V4_W4A8_*` knobs falls back to the launch default
  `K8V4_PREFILL_GEMM=w4a8`, which is per-token W4A8 on the MLP. So `e1` is close to `a1`'s config, not a
  bf16-activation arm. That is why `e1` (.025) > `f1` (.0066).
- **`a1` vs `a2` (same config, same cache directory, no determinism flag): median .027, top-1 36/40.** This is as
  large as the claimed drift. The cause is the oneDNN `in_proj_ba` reduction-order nondeterminism that
  `K8V4_ONEDNN_DETERMINISTIC` fixes.

## 3. Mechanism (offline, real Q/K/V, no server noise)

Capture method:
- `K8V4_KVDUMP` (test tree only) saved, for every prefill chunk of the 16 full-attention layers, the pre-store
  bf16 K/V and every 8th query row plus the last 128.
- It was run on two lpcheck prompts, each a fresh salted prefill from token 0:
  - code cut 8, 18,144 tokens: the 8-nat cut, which also gave `' delta'` 0.993 here;
  - prose cut 19, 43,271 tokens.

Analysis method:
- a local analysis script (CPU, fp32 reference) applies each candidate store with the kernel's
  exact arithmetic and measures the attention-output error against exact attention.
- Sample: 384 query rows per layer (all 24 heads), the last 128 = "end".

Their store (`xe2_kv_ops.cpp` `launch_k_store_paged` / `launch_v_store_paged`, input cast to fp16 first):
- K: one fp32 scale per (token, KV head) = amax/127 over the 256 channels, `rint`, clamp ±127. Symmetric, no
  zero point.
- V: one fp32 scale + one fp32 zero per (token, KV head) over all 256 channels. Scale = (max-min)/15,
  zero = round(-min/scale) clamped to 0..15, `floor(x/scale+zero+0.5)`. The group is the whole head (256).
- Decode additionally quantizes Q per (token, head) to int8 and scores in int8 x int8.
- Prefill dequantizes the *whole* sequence, including the current chunk, from the cache into fp16 and runs
  oneDNN SDPA in fp16. So a long prefill sees the quantized K/V for every row.

Findings:
- **V int4 is the whole effect:** 7 % against K int8's 0.5 %. Removing the K error changes nothing (K8V4 0.0720
  vs V4 alone 0.0718). Against fp8, K8V4 is 2.7x (18K) and 2.5x (43K). GRIMOIRE's simulation said 9.2 % vs 2.7 %
  (3.4x); this is the same picture on real activations.
- **No Qwen-style K outlier problem on this model.**
  - Channel rms max/median per head is 2-8 and the per-token crest factor (amax/rms) is 3.5-5.1.
  - So per-token int8 K costs only 0.3-0.8 % per layer.
  - Outlier handling, rotation or per-channel scales cut K from 0.5 % to 0.3 %, which does not matter next to V.
- **V is nearly Gaussian per token** (crest 3.7-5.0; 7.3 in layer 59). That is why int4 cannot be rescued by scale
  tricks:
  - Smaller groups and rotation each take 25-30 % off.
  - Both together take 38 % off: 0.072 to 0.044, still 1.7x fp8.
  - Rounding mode and scale dtype do not matter. The integer zero point is *better* than a fractional one at
    the end rows, and fp16 scale/zero equals fp32.
- **No sink.** The first 4 tokens get ~0-2 % of the attention mass at the end rows, so exact sink tokens do
  nothing (0.072 to 0.071). A recent-token window helps decode-like rows: 128 exact tokens take 0.072 to 0.043
  at 18K, but only 0.068 to 0.051 at 43K.
- **No growth with context or depth.** The error is flat from 2K to 43K. It is highest below 2K tokens (0.12-0.13,
  fewer keys to average) and spread over depth (layer 3 lowest at 4.9-5.6 %, the 7-23 and 47-55 blocks at
  7-9 %).
- **The 8-nat cut is a V-int4 effect that tips a bistable position:**
  - It reproduces with W4A8 off and with per-token W4A8.
  - It reproduces on the stock bf16 kernel with only the V rounding (`zV`).
  - It does not reproduce with int8 K alone, fp8, V g64, Hadamard, K8V8, or with grouped W4A8 upstream.
  - The 0.999 confidence comes from the model itself, which latches onto a completion once the context reads
    slightly differently. It is not a numerical fault: no NaN or overflow, and the 18K capture shows the same
    5-9 % per-layer error as everywhere else.

## 4. Fix: `K8V4_KV_ROTATE` (opt-in, branch `b70/kv-drift`)

How it works:
- `K8V4_KV_ROTATE=v` (or `k`, `kv`) multiplies each 256-wide K and/or V head vector by an orthonormal Sylvester
  Hadamard matrix H (fp32) before the K8V4 store.
- For `k` it also multiplies the query by H. For `v` it multiplies the attention output by H afterwards
  (P (V H) H = P V).
- It is exact without quantization and spreads each vector's large channels over all 256, so the per-token
  int4 / int8 scale is set by a flatter vector.

What stays the same:
- No kernel, layout or capacity change. Unset leaves every tensor and the launch command unchanged, and a bad
  value is refused.
- Numerics: changes the stored values (lossy-to-lossy), not bit-identical to the default.

Tests:
- `k8v4_v030/tests/test_kv_rotate.py`: parsing, orthonormality, exact attention equivalence, and a smaller K8V4
  round-trip error on an outlier vector.
- `test_launch_profiles`: the default command is unchanged and the knob is passed only when set.

Measured end to end on the real K8V4 backend (W4A8 off, det, cache from kO1, reference bO1). Step time is
`l3step.py`, warm 63K prefixes, p50 inter-chunk gap over 3 x 512 tokens:

Results:
- Capacity is unchanged.
- The 8-nat cut is gone in both arms.
- The mean KL falls 10x for `v` and 6x for `kv`. Both are now below fp8's mean, which one knife-edge cut
  dominates.
- The median falls by a third (`v`) or a half (`kv`), but stays at 2-3x fp8's median.
- `rKV`'s extra flip and its max are code cut 5, the three-way tie that also flips under int8-K-only and fp8.
  Its remaining top-1 differences are near-ties at ~0.005-0.03 nats.
- Cost: one fp32 [rows, 256] x [256, 256] matmul each for the store, the query (`k`) and the output (`v`), which is
  0.6-1.8 % of a decode step. Fusing the rotation into the store / q-quant kernels would remove most of it but
  was not built.
- The step-time setup is their default decode config (no `XE2_KV_S1_SPLITS`, etc.), so read the steps as
  relative numbers.
- Recommendation if their users want it: **`K8V4_KV_ROTATE=v`**. It removes the large flips and keeps the
  capacity, for <1 ms per step. It does not reach fp8's median, because int4 V on near-Gaussian vectors has a
  floor around 5 % attention error.

Also measured, not usable: `bP1` / `kP1`, which add their per-token W4A8 to bO1 / kO1 using those arms' compile
caches.
- Both came out bit-equal to the W4A8-off arms. The log shows `MLP-only installer active`, but `Directly load
  AOT compilation`.
- The TP1 profile's cache namespace is the fixed `w4a8-tp1-v1` for every `K8V4_PREFILL_GEMM`. So a cache built
  with `w4a16` silently serves a W4A8 start without the W4A8 path, and the reverse is likely too.
- This is a trap for anyone switching that knob on one `K8V4_CACHE`. Every arm in the tables above used a
  cache built with its own W4A8 mode.
