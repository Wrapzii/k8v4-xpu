# W4A8 prefill: fused post-attention add + RMSNorm quantizer (K8V4_W4A8_FUSED=addnorm) — November 19, 2026

One Arc Pro B70, Swift 1.5 (Qwen3.8-27B GPTQ int4 g128, bf16), TP1, vLLM 0.34. Port of our production
`B70_W4A8_ADDNORM`. Off unless set; with the knob unset the launch command and the math are unchanged.

## What it does

`K8V4_W4A8_FUSED=addnorm` (with `K8V4_W4A8_KERNEL=onednn`; `mlp` in `K8V4_W4A8_LAYERS`): in every decoder
layer, the residual add, the Gemma RMSNorm (`post_attention_layernorm`) and the int8 quantization of
`gate_up_proj`'s input run as one Triton pass inside `gate_up_proj`'s op (`k8v4_prefill::addnorm_gemm`), which
also writes the new residual. The normed `[tokens, 5120]` activation is never written out and read back.
Per-token scales (the best config) or grouped ones (`K8V4_W4A8_AGROUP`); unlike `silu` / `gnorm`, `addnorm`
does not need `AGROUP`. Rows at or below 128 (decode, verify) get the same add + norm unquantized from the
same kernel and the library w4a16 GEMM. Combines with `silu` (the down projection then takes its fused op).

- `Qwen3_5DecoderLayer` gets a forward that is the stock `Qwen3NextDecoderLayer.forward` with the norm and
  the MLP's first GEMM merged. It is installed by an import hook (no file overlay); the installer checks the
  installed vLLM source for its seven anchor lines and refuses an unknown forward, or a class that defines
  its own. Layers with `layer_scale`, sequence-parallel MoE, an expert gate, no residual (the first layer, the
  MTP draft layer) or an unmarked `gate_up_proj` run the stock forward.
- `launch.sh` validates the comma list (silu, gnorm, addnorm; no repeats) and gives it its own compile-cache
  namespace.

Tests: `tests/test_w4a8_fused.py` (parse rules; fused == norm-then-quantize, per token and grouped; dispatch
by row count; only marked layers take the op; source check refuses), `tests/test_w4a8_triton_xpu.py::
test_addnorm` (XPU: residual bit-equal to the reference, codes within one step), `tests/test_launch_profiles.py`.
The XPU run also showed a failure in the existing `test_quantizers` gnorm tolerance check (line 48), which
this change does not touch.

## Microbenchmark (one B70, bf16, hidden 5,120; `bench/addnorm_bench.py`)

Stock = vLLM's XPU `xpu_fused_add_gemma_rms_norm` followed by the Triton quantizer; fused = this kernel.

| rows | scales | stock | fused | x 64 layers |
|---:|---|---:|---:|---|
| 4,224 | per token | 0.474 ms | 0.331 ms | 30.3 -> 21.2 ms |
| 4,224 | 64 channels | 0.468 ms | 0.328 ms | 29.9 -> 21.0 ms |
| 8,192 | per token | 0.893 ms | 0.615 ms | 57.1 -> 39.4 ms |
| 8,192 | 64 channels | 0.895 ms | 0.607 ms | 57.3 -> 38.8 ms |

The new residual is bit-identical to the stock op's. Against the stock op's normed output the int8 codes differ
by at most 2 steps and some scales differ: the stock XPU norm kernel rounds differently from vLLM's
`forward_native` formula, which the fused kernel follows (the CPU test checks it equals that formula exactly).

## Numerics

Changes numerics slightly (not bit-identical): the normed activation is computed by the Triton kernel with
vLLM's `forward_native` formula instead of the XPU norm kernel, so int8 codes can differ by 1-2 steps on
prefill rows, and decode rows go through the same kernel unquantized (normed values can differ in the last
bf16 bit from the stock XPU norm). The residual stream is bit-identical. EXACT stayed 8/9. QualityBench was not
run (speed parity first).

## Verdict

Works, opt-in, small: the add + norm + quantize is ~1% of a 63K prefill on this stack, so fusing it gains
~0.3-0.4%: the stock path here already uses vLLM's fused XPU add-norm op and a one-pass Triton quantizer.
