# September 30 update: natural-EOS decode and a 262K serving window

The new coding workload reaches a median **62.49 tok/s at 200,156 prompt tokens** on K8/V4. A second task that also retrieves two constants from the beginning of the document reaches **65.04 tok/s at 200,155 tokens**. Every measured answer stops naturally and passes syntax and independent behavior checks. These results establish the 60 tok/s target for these workloads; they are not a guarantee for every task or for four concurrent users.

## New single-stream measurements

One warmup followed by three measured requests per point, temperature 0, MTP 6. The task implements `merge_intervals` with validation and no input mutation. The retrieval variant additionally implements `load_limits()` using constants placed before the filler text.

| prompt tokens | K8/V4 median tok/s | stock FP8 median tok/s | K8/V4 median update gap |
| ---: | ---: | ---: | ---: |
| 2,153 | 137.87 | 146.26 | 39.09 ms |
| 8,159 | 128.63 | 131.89 | 40.95 ms |
| 32,157 | 116.67 | not measured | 46.85 ms |
| 127,863 | 77.06 | not measured | 70.05 ms |
| 200,156 | 62.49 | not measured | 87.90 ms |
| 200,155, with retrieval | 65.04 | not measured | 87.89 ms |

The ordinary 200K samples are 62.49, 59.67 and 63.28 tok/s; the retrieval samples are 66.06, 62.06 and 65.04. Thus even this successful median is not a claim that every run exceeds 60.

Rate is `(last cumulative tokens - first cumulative tokens) / (last event time - first event time)`: the entire first streamed update is excluded. Update gaps are verifier/serving steps, not per-token latency and not isolated attention timings. Prefix caching is enabled; repeated prompts reuse prefixes. These runs do not establish cold prefill throughput. `quality.embedded_tests` is a legacy field name for independent client assertions, not tests supplied by the model.

The older fox curves and BetterBench results remain under their original headings in README and RESULTS. The fox client forces 96 tokens with `ignore_eos`; some completions contain post-EOS control tokens. Do not mix those rates with the new natural-EOS coding curve. New FP8 comparisons cover only 2K and 8K. The new data does not establish a win over FP8 across all workloads.

## What changed

GPU 0 had a configured 1,800 MHz ceiling while GPU 1 allowed 2,400 MHz. Both ceilings were restored to 2,400 MHz with the existing 180 W burst limit. Short-context results also use a different task and different MTP acceptance, so the speed increase cannot be attributed entirely to the clock correction.

Stage-2 subgroup selection now distinguishes the one-row draft from the seven-row verifier:

| variable | serving default | purpose |
| --- | ---: | --- |
| `XE2_KV_S2_NSG_DRAFT` | 32 | one query row |
| `XE2_KV_S2_NSG_VERIFY` | 8 | multiple query rows |
| `XE2_KV_S2_NSG` | 32 | native fallback if the role-specific setting is absent |
| `XE2_KV_S2_TWO_PASS` | 0 | optional experimental merge; leave disabled |

The native library still defaults to the original stage-2 algorithm. Role-specific environment settings override the fallback. To reproduce the previous subgroup choice under the new launcher, set both role-specific settings to 32.

A standalone XPU graph sweep measures host time around repeated graph replays, including query quantization and both attention stages. It uses no device timestamp instrumentation. Every accepted graph is compared with NSG=32 output. At 200K, NSG=8 improved the seven-row path by roughly 1.5–1.8%, but slowed the one-row path by roughly 9%. Smaller contexts showed larger verifier gains. This justified independent choices rather than changing both to 8.

An experimental two-pass merge is included in the exact tested source for reproducibility, but is disabled: it was correct and slower at long context. No performance claim uses it.

The graph sweep is synthetic, uses one attention layer and includes host replay overhead. It establishes a relative kernel choice, not a pure GPU attention time for all 16 full-attention layers. The older wrapper's zero decode-call count under graph replay was not an attention timing measurement. Hung timestamp binaries were not used.

Four strengthened XPU tests passed on both ranks with draft=32, verifier=8 and two-pass=0. They cover 59,500 and 59,527 tokens, 63,932 and 70,000 tokens, independent sequence references, partial pages, negative slots, prefix copy-on-write, dirty tails and V-scale changes. The 59.5K parallel-versus-serial difference was about 3.8e-6. The recorded results identify the tested library; a later lightweight restore check verifies the same mounted library is selected by the live container. Compilation and CPU checks alone do not constitute live serving validation.

[live-restore.json](../results/2026-09-30/live-restore.json) records the running library, native source, Python file hashes, selected flags, health status, enabled service and zero CAT errors. Every recorded Python file matches the published package. Local CPU checks completed 77 tests with the four XPU tests skipped locally; those four passed separately on the server.

Source review also found an existing V-quantizer edge case: the scale uses `(max-min)/15` while the zero point is clamped to `[0,15]`. Entirely positive or entirely negative rows can clip excessively; a nonzero constant row degenerates to nearly zero after dequantization. The signed random-vector gates and selected model tasks do not establish correctness for those inputs. This behavior is unchanged in the tested/published library; no untested quantizer fix was promoted.

On a host with limited RAM, stop the model before compiling. Use bounded, standalone kernel probes first, then one serving stack at a time. Do not load a second model merely to profile attention.

## Benchmark configuration versus deployment

The K8/V4 single-stream curve used max length **200,640**, max sequences **8**, batch-token cap **8,192**, GPU memory utilization **0.90**, TP2, MTP6 and `FULL_DECODE_ONLY`. FP8 used its stock 131,072-window profile with the same small prompts. Both use the local GPTQ INT4 bake, int8 embedding, bf16 activations, PCIe two-shot all-reduce and thinking disabled.

The new deployment defaults are **262,144** maximum tokens per request, **4** active sequences, **4,224** batch tokens, utilization **0.95**, and graph sizes `[7,14,21,28]`. The running B60 deployment reported **814,581 tokens of shared KV capacity**, or 3.11 full 262K windows. This is a shared pool, not 262K reserved separately for each user. Four full 262K histories cannot all remain resident. Four histories around 131K require about 524K tokens before outputs and other overhead, which fits the reported pool.

vLLM reserves weights, graph/workspace memory and KV pool within the configured GPU budget. Increasing `max-model-len` changes the allowed request window; it does not create additional VRAM. Prefix reuse can save capacity; this capacity check uses different histories to avoid depending on it.

Completed live requests validate four different **130,080-token histories**, with two rounds and eight passing natural-EOS answers. Each retrieves its own marker from the beginning and returns the correct 100-integer sequence. The initial run observed four running requests, peak pool usage 72.51%, and no preemptions. Its prompt did not specify the marker's JSON type: six answers returned the correct digits as strings, failing the original strict integer check. Those original check results remain in the raw export. Requiring an integer explicitly passed all eight subsequent four-history answers.

A separate request with **261,055 prompt tokens plus 405 output tokens** stopped naturally and retrieved the correct marker. Time to first token was **327.49 seconds**, or **797.14 prompt tokens/s** when divided into TTFT. This includes serving overhead and is one capacity-validation observation, not a repeated cold-prefill benchmark. There is no matching pre-clock 261K run from which to attribute a speedup. The duplicate near-maximum request was canceled when the user asked to stop extra testing; no result is claimed for that canceled request. See [capacity-summary.json](../results/2026-09-30/capacity-summary.json), [initial raw records](../results/2026-09-30/capacity-initial.jsonl) and [explicit-type raw records](../results/2026-09-30/capacity-explicit.jsonl).

Long cold prefills delay other streams; concurrency capacity does not imply 60 tok/s per user. The initial cached four-request round finished in roughly 29–33 seconds for 405-token answers, including its remaining prefill and scheduling delay. These timings are observations rather than an isolated concurrency speed comparison.

The portable launcher publishes loopback port 8200 by default and leaves restart policy off. The deployed instance uses a private network endpoint and an enabled systemd service, with Docker `unless-stopped`. Its previous FP8 autostart service is disabled. GPU tuning is ordered before Docker without the previous `multi-user.target` ordering cycle. These host-specific paths and addresses are intentionally absent from the portable launcher.

## Reproduce

Build and launch using the README instructions. For the measured single-stream profile:

```bash
K8V4_MAX_MODEL_LEN=200640 K8V4_MAX_SEQS=8 \
K8V4_MAX_BATCHED_TOKENS=8192 K8V4_GPU_MEMORY_UTILIZATION=0.90 \
MODEL_DIR=/path/to/model bash k8v4_v030/launch.sh
python3 bench/serve_coding.py --base http://127.0.0.1:8200 \
  --lengths 2000,8000,32000,127700,200000 --max-tokens 448
python3 bench/serve_coding.py --base http://127.0.0.1:8200 \
  --lengths 200000 --max-tokens 448 --needle
```

The small/middle recorded runs used a 768-token output cap; 200K used 448. All outputs stopped below their cap. The command above uses 448 throughout to fit the longest point safely.

Inside the matching XPU runtime, with the server idle, use a bounded synthetic sweep and require the tested library hash:

```bash
XE2_KV_LIB=/path/to/libxe2_kv.so PYTHONPATH=. \
python3 bench/graph_sweep.py --lengths 2001,8001,127853,200000 \
  --queries 1,7 --device 0 --capacity 200640 --pages-per-block 33 \
  --repeats 9 --replays 48 --warmup 64
K8V4_REQUIRE_TP2=1 XE2_KV_S2_NSG_DRAFT=32 XE2_KV_S2_NSG_VERIFY=8 \
XE2_KV_S2_TWO_PASS=0 python3 -m unittest k8v4_v030.tests.test_kernel_xpu
```

## Hermes

Both installed Hermes clients were configured for the same local served model, explicit 262,144 context and compression threshold 0.5. A real `read_file` tool request returned the expected distinct marker through each client's configured route. The server client uses loopback; a remote client uses its reachable private endpoint. Existing provider entries and credentials were preserved, with config backups.

For another installation, merge the following fields into its existing `config.yaml`, replacing `YOUR_HOST` and the model alias when needed:

```yaml
model:
  provider: k8v4
  default: Qwen3.8-27B-GPTQ-Int4-baked-v2-embed-int8
  base_url: http://YOUR_HOST:8200/v1
  api_mode: chat_completions
  context_length: 262144
providers:
  k8v4:
    name: K8/V4 Qwen 27B
    base_url: http://YOUR_HOST:8200/v1
    api_key: EMPTY
    transport: chat_completions
    default_model: Qwen3.8-27B-GPTQ-Int4-baked-v2-embed-int8
    context_length: 262144
    models:
      Qwen3.8-27B-GPTQ-Int4-baked-v2-embed-int8:
        context_length: 262144
    extra_body:
      chat_template_kwargs:
        enable_thinking: false
compression:
  enabled: true
  threshold: 0.5
auxiliary:
  compression:
    provider: main
    model: Qwen3.8-27B-GPTQ-Int4-baked-v2-embed-int8
    timeout: 600
```

Named providers and context overrides are documented in the [Hermes provider guide](https://hermes-agent.nousresearch.com/docs/integrations/providers/); compression configuration is described in the [configuration guide](https://hermes-agent.nousresearch.com/docs/user-guide/configuration/). Compaction is triggered near the threshold with prompt/tool budgeting, not a strict VRAM partition or a guarantee that four clients can never exceed shared capacity. Existing sessions with a stored model override can retain that override; new chats use the configured default.
