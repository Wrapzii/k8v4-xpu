The new deployment instead allows 262144, four sequences, batch cap 4224 and utilization 0.95; its shared KV pool is 814581 tokens. All new measurements use TP2, MTP6, bf16 activations, oneDNN prefill and MLP-only W4A8. Small-context FP8 is a stock 131072-window profile. Long-context FP8 was not remeasured on this coding task.

[Raw data and summary](results/2026-09-30/) include full answers and streaming events. See the [dated update](docs/2026-09-30-update.md) for hashes, graph sweeps, correctness gates and reproduction. The earlier tables below use different workloads and retain their original values.

Live deployment validation completed two four-request rounds at 130,080 prompt tokens per independent history, all eight answers passing retrieval and explicit JSON-type checks. A separate 261,055-token prompt with 405 output tokens passed retrieval and stopped naturally. Its TTFT was 327.49 s, equivalent to 797.14 prompt tokens/s including serving overhead; this is a single observation, with no matched pre-clock comparison. Raw results preserve the earlier strict-type failures on correct quoted markers and the later successful explicit-type prompt. ## Attention KV bytes

From `k8v4_v030/layout.py`, TP-local, one full-attention layer:

- FP8: 1,024 bytes per token
- K8/V4, scales included: 792 bytes per token
- Saved on that layer: 232 bytes (22.7%)

16 full-attention layers, both GPUs: 7,424 bytes saved per token. At 131,072 tokens that is 928 MiB (4.00 GiB FP8, 3.09 GiB K8/V4). At the measured 127,853-token prompt it is 905 MiB. GDN state on the other 48 layers is not in this layout.

Reported pool usage at 127,853 tokens: K8/V4 0.199, FP8 0.241. Peak resident memory on that K8/V4 point: 23,583 / 23,223 MiB. FP8 resident stayed 23,002 / 22,638 MiB across the curve.

## Stock FP8 prefill, one change at a time

Fox prompt, rate is actual prompt tokens over time to first token. Control is FP8, FlashAttention v2, prefix caching on, block 1664, batched tokens 8192. Clocks 2400 MHz. Power under the 180 W cap.

| change | ~8K tok/s | ~47K tok/s |
| --- | ---: | ---: |
| none | 1680 | 1288 |
| batched tokens 8192 to 4096 | 1683 | 1271 |
| prefix caching off | 1731 | 1295 |
| `kv-cache-dtype=auto` (bf16 KV, block 832) | 1764 | 1517 |

bf16 KV helps the long point and cuts pool capacity (about 4.2 contexts down to about 2.25). It was not adopted. A Triton attention backend was tried once, hung a long prefill, and faulted the copy engine. It was not repeated.
